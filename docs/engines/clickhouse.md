# ClickHouse

Written: 2026-10-29 · Status: implemented

Engine definition `clickhouse` (alias `ch`), driver in `crates/tablepeek-engine/src/engines/clickhouse/`, web code in `web/src/engines/clickhouse/`. The paradigm is `sql`, and it uses the SQL workbench as is.

## 1. Scope

- Supported servers: ClickHouse 22.x and later (tested on 25.8). It connects over the HTTP interface (default 8123, HTTPS 8443). The native TCP protocol (9000) is not used.
- The HTTP client is `reqwest` (rustls), which the engine crate already uses. There are no new dependencies. The official `clickhouse` crate is not used because it only reads results into predefined Rust types and can't show arbitrary queries.
- Results are requested as `JSONCompactEachRowWithNamesAndTypes` and read line by line. 64-bit integers and Decimals are received as strings to keep exact values, and integers that fit in i64 are converted to numbers. Past the maximum row count, reading the response stops (`cancel_http_readonly_queries_on_client_close`) and the result is marked "Truncated". When a statement sets its own format, like `FORMAT CSV`, its output is shown line by line in one column (named after the format).
- Editor statements run in one HTTP session (`session_id`), so `USE` and `SET` carry over to the next statement. A session only accepts one statement at a time, so the driver keeps them in order. Catalog reads, edits and exports are sent outside the session with the current database specified.

## 2. Connecting

| config key | Meaning |
|---|---|
| `host`, `port` | Defaults `127.0.0.1`, `8123`. HTTPS is usually `8443` |
| `user` | Default `default` |
| `password` (secret) | Sent in the `X-ClickHouse-Key` header (never in the URL) |
| `database` | Becomes the session's database with `USE` after connecting. When empty, the user's default database |
| `tls` | bool. When on, `https` |
| `tls_ca_file` | PEM CA (may hold several certificates). Without it, the system roots |
| `tls_skip_verify` | bool. Don't verify the certificate (for development, advanced) |
| `cluster` | Cluster name (advanced). Default `ON CLUSTER` for structure changes the app writes (§5) |

- Pasting a connection URL `clickhouse://user:pw@host:8123/db` (or `ch://`) into the host field fills in the fields. `?secure=true` is not read, so turn on HTTPS with the toggle.
- SSH and HTTP tunnels: when the tunnel endpoint is an IP, the original host name is resolved to that address (`resolve`), so the HTTPS certificate name check (including SNI) still uses the original name through the tunnel. reqwest connects to the URL's port, so the URL port is the tunnel endpoint's port, and the `Host` header sends the configured `host:port` unchanged (verified in §10 through an SSH server and an HTTP proxy to `clickhouse.tablepeek.test`; names not in the certificate are rejected).
- On connect it reads `SELECT version(), currentDatabase(), getSetting('readonly')`. For a read-only account (`readonly` ≠ 0), editing, DDL, users, indexes and import are turned off, and for an account that can't read `system.users`, user management is turned off (`meta.capabilities`).

## 4. Row editing

ClickHouse has no unique keys. The data tab uses the table's **sorting key** (`ORDER BY`) columns as the key, and enables editing for MergeTree-family tables and Distributed tables on top of them (views, dictionaries, Memory, Log and the like are read-only).

- **Telling rows with the same key apart**: for tables with a sorting key, the data tab also reads the virtual columns `_part` (the data part holding the row) and `_part_offset` (the position within the part) after the columns (`SqlDialect.rowIdentity`). When both are in the result, the driver appends them to the key, and edits and deletes find the row by that part and position along with the key. Mutations (cell updates, lightweight DELETE) rename the part by appending the mutation number but leave row positions unchanged, so the condition `_part = 'p' OR startsWith(_part, 'p_')` (`p` = `partition_min_max_level`) also finds the same part after renaming. On servers before 23.3, deletes remove rows from the part, so only the exact name that was read is matched. Exports leave out both columns. Query editor results behave the same if you add `_part, _part_offset` to the SELECT.
- **Finding again**: edits and deletes also send the last values the grid knew for all columns of the row (`seen`, docs/ENGINES.md §4.1; reflecting values already written by the same apply on top of the values read). When a row can't be found by part and position because a merge (background, `OPTIMIZE`) moved it to a new part, or when only the key is present without part and position and several rows match, the driver counts again with the sorting key + all values (`col = CAST(…)`, `isNull` for NULL) and switches to that condition when it matches **exactly one row**. If several rows have all values equal, it rejects ("정렬 키와 모든 컬럼 값이 같은 행이 여럿…"), and if the values have already changed, it is 0 rows. Types that can't be compared for equality (AggregateFunction, JSON, Object, Dynamic, Variant, geo types, tuples inside arrays or maps) are left out of the condition.
- Before an edit or delete, it checks that the current sorting key equals the key the grid received, and counts the rows matching that condition. It changes the row only when there is exactly 1; with 0 it changes nothing (0 rows), and with 2 or more (if the values above can't tell them apart either) it rejects.
- **Tables the sidebar doesn't know yet** (just created): before the first page, the data tab reads the sorting key from `/api/table`, so it reads `_part, _part_offset` from the first page on.
- Cell updates: on servers 25.7 and later, if the table has `enable_block_number_column = 1` and `enable_block_offset_column = 1` (checked in `system.tables.create_table_query`, including when turned on later with `MODIFY SETTING`), it is a **lightweight UPDATE** `UPDATE … SET col = CAST(value AS type) WHERE …` (`allow_experimental_lightweight_update = 1`; it writes a patch part and finishes right away). Otherwise it is an `ALTER TABLE … UPDATE … WHERE … SETTINGS mutations_sync = 2` **mutation**, which rewrites data parts, and it waits until that finishes. **Turn on** next to the table property "Lightweight UPDATE: Off" in the structure tab, after an explanation and confirmation, runs `ALTER TABLE … MODIFY SETTING enable_block_number_column = 1, enable_block_offset_column = 1` so later cell updates use lightweight UPDATE (§5). The server rejects sorting and partition key columns (the error help explains).
- Deleting rows: lightweight `DELETE FROM … WHERE …` for MergeTree on 23.3 and later, `ALTER TABLE … DELETE` on older servers. Both wait with `mutations_sync = 2`.
- Adding rows: `INSERT INTO … VALUES (CAST(…), …)`. When every column is default, `INSERT … FORMAT JSONEachRow {}`.
- Values are the text the grid showed, `CAST` to the column type. The grid shows Array, Map and Tuple as JSON, so values edited as JSON are converted to ClickHouse literals (`[…]`, `map(…)`, `tuple(…)`) before sending. NOW in Set Value is `now64(6)`, and DEFAULT is the column's DEFAULT expression (or the type's default if there is none).
- **Undo for multi-cell applies**: there are no transactions, so when one statement fails partway through an apply, the web app reverses the changes that went in before it (cells back to their original values, deleted rows inserted again, added rows deleted; docs/ENGINES.md §4.1 compensating undo). The error message lists the reverted changes and any that couldn't be reverted, with reasons.
- **Rows in a cluster**: edits and deletes on a Distributed table go to the local table its engine points to, becoming `ALTER TABLE local ON CLUSTER c UPDATE …`, `UPDATE local ON CLUSTER c SET …` or `DELETE FROM local ON CLUSTER c …` (the key is the local table's sorting key, and the structure view and sidebar also show those columns as the key). When a non-replicated MergeTree table also exists on the other servers of the connection setting `cluster` (a table created with ON CLUSTER, checked with `clusterAllReplicas(c, system.tables)`), its edits and deletes also go to the same row on every server with `ON CLUSTER c`. Part names differ per server, so in this case the row is found by sorting key + all values, and it checks with `clusterAllReplicas(c, db, t)` that no server has more than one such row, and for a Distributed table, reads through that table to confirm exactly one row across all shards. Replicated tables are left as they are, since a change on the connected server is spread by replication.

## 5. Structure

- Columns: name, type (including Nullable and LowCardinality), default (MATERIALIZED, ALIAS and EPHEMERAL with their kind), Enum value list. Sorting key columns are marked as "primary key".
- Indexes: data skipping indexes (`system.data_skipping_indices`) and their definitions.
- **Table properties** (`TableDetail.properties`): engine, ORDER BY, PRIMARY KEY (when it differs from the sorting key), PARTITION BY, SAMPLE BY, TTL, SETTINGS, active part count, uncompressed size, and for MergeTree tables on servers 25.7 and later, **Lightweight UPDATE** (On/Off: the block number and offset column settings). Shown in the "Table properties" panel below the structure view (hidden with the "Properties" button at the bottom). **Turn on** next to "Off" (`SqlDialect.propertyAction`) explains what changes (cell updates use patch parts instead of mutations, and each row stores an extra block number and offset), opens a confirmation dialog showing the statement to run, and then runs `ALTER TABLE t MODIFY SETTING enable_block_number_column = 1, enable_block_offset_column = 1`. It follows the structure tab's ON CLUSTER choice.
- DDL: `SHOW CREATE TABLE` (`SHOW CREATE DICTIONARY` for dictionaries).
- Structure editing: adding a column is `ADD COLUMN name type [DEFAULT …]` (nullability goes into the type as `Nullable(…)`), changing is `MODIFY COLUMN` (`REMOVE DEFAULT` when the default is cleared), renaming `RENAME COLUMN`, key changes `MODIFY ORDER BY` (the server only accepts appending columns newly added in the same ALTER). Indexes are `ALTER TABLE … ADD INDEX name (column) TYPE minmax GRANULARITY 1` / `DROP INDEX`; existing parts only get the index after a separate `MATERIALIZE INDEX`.
- Creating tables: with a key, `PRIMARY KEY (…)` + `ENGINE = MergeTree`; without, `ENGINE = MergeTree ORDER BY tuple()`.
- **ON CLUSTER** (`SqlDialect.clusters`): when `system.clusters` has clusters, an "ON CLUSTER" list appears in the create table dialog and at the top of the structure tab's "DDL preview". Choosing "This server only" or a cluster makes both the preview and the executed statements `CREATE TABLE name ON CLUSTER c …` and `ALTER TABLE name ON CLUSTER c …`. The initial choice is the connection setting `cluster` (saving without opening the preview also follows it), and in the sidebar, rename (`RENAME TABLE … ON CLUSTER c`), duplicate (`CREATE TABLE … ON CLUSTER c AS …`; the row-copying INSERT runs only on the connected server), truncate and drop follow that setting too, with "클러스터 c의 모든 서버에서 실행합니다" added to the confirmation dialog. Editor statements and templates are not changed. The server waits for results from all servers through the `distributed_ddl` queue and returns an error if any server fails.

## 6. Execution plan

- The execution plan button prepends `EXPLAIN json = 1, actions = 1, indexes = 1`. The JSON, which arrives split over several lines, is joined and drawn as a step tree, and table read steps show "selected parts/granules · condition" per index. Reads where the index didn't filter out any granules are shown in a warning color.
- Hand-written `EXPLAIN PLAN` and `EXPLAIN PIPELINE` (indented text) are also drawn as trees, and `EXPLAIN ESTIMATE` (parts, rows and marks per table) as a read list. The snippets include PIPELINE and ESTIMATE.

## 7. Export, import and dump

- Exporting a table (or chosen columns) as CSV or JSON goes through `POST /api/sql/export`, where the server streams `SELECT … FORMAT CSVWithNames` (`CSV` without a header) or `FORMAT JSONEachRow` (`output_format_json_array_of_rows = 1`, a JSON array) directly. There is no row limit and no paging. Of the CSV options, delimiter, header, line ending (CRLF/LF), NULL notation (empty/`NULL`) and BOM are honored; quote replacement, decimal comma and newlines-as-spaces can't be done by the server, so in those cases it writes through the grid as before. Query results, Excel and SQL exports use the existing path.
- CSV option **"Arrays, maps and tuples as JSON"** (`nested_json`): when off, the server's CSV format (`"['a','b']"`, `"{'k':2}"`, `"(1,'x')"`); when on, the JSON the grid shows (`"[""a"",""b""]"`). The server reads the result column types with `DESCRIBE TABLE (statement)` and rewrites only Array, Map, Tuple and Nested columns as `SELECT * REPLACE (toJSONString(c) AS c, …) FROM (statement)` (same JSON settings as the grid: 64-bit integers and Decimals quoted, tuples as arrays).
- CSV and JSON import (the "insert" mode) sends 10,000 rows at a time as `INSERT INTO t (…) FORMAT CSV`. The server parses each value as the column type, and NULL is `\N`. There are no transactions, so on failure the batches before it are already in (the import dialog says so). To find the failing row, it retries one row at a time with VALUES.
- Dump and SQL export: `SHOW CREATE TABLE` statements (including engine and ORDER BY) and INSERTs. Restore runs the statements one by one (no transaction).

## 8. Sessions, timeouts and logs

- Server info: version, current database, uptime (`uptime()`), database size (sum of active parts), running queries (`system.processes`: query_id, user, database, state, query, elapsed). Ending a session is `KILL QUERY WHERE query_id = '…' ASYNC`. The query that reads the server info itself is shown as "current".
- Cancel: sends `KILL QUERY` with the running statement's query_id. A stopped statement is `interrupted` (code 394).
- The "query timeout (seconds)" setting goes with each editor statement as `max_execution_time` (0 means the server setting). Exceeding it gives code 159 and its help.
- Every statement (including catalog reads) is logged to the console. Errors carry the code (`clickhouse_62`), name (`SYNTAX_ERROR`), position ("at position N" as a character position) and original message.

## 9. MCP

The SQL engines' read-only tools (`tablepeek_list_tables`, `tablepeek_describe_table`, `tablepeek_query`) work as is. Write statements (`ALTER … DELETE` and the like) are rejected.

## 11. Limits

- When several rows match on the sorting key and every column value, there is no way to tell which is which once a merge has changed their parts and positions, so the edit is rejected (refreshing tells them apart again by the new parts and positions). Part and position are the only information that distinguishes rows with identical content.
- **Added rows** in a non-replicated cluster table go only to the connected server. ClickHouse's INSERT has no `ON CLUSTER` (INSERT syntax: `INSERT INTO [TABLE] [db.]table [(c1, …)] [SETTINGS …] VALUES …`; `ON CLUSTER` is accepted only by distributed DDL and the ALTER and lightweight UPDATE/DELETE built on it). To insert on every server, insert through a Distributed table with `internal_replication = false` (adding a row in the data tab goes to that table). For the same reason, import also follows the connected server (or the sharding rule of the chosen Distributed table).
- Compensating undo is not a transaction: if someone else changes the same row while it is being reverted, that revert fails with 0 rows and is listed under "remaining changes" in the error message. For rows whose sorting key was changed with DEFAULT or NOW, the key the DB chose is unknown, so the message says they can't be reverted.
