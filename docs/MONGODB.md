# MongoDB support spec

Written: 2026-10-28 · Status: phases 1–4 implemented · UI reference: `prototypes/mongodb/tablepeek-mongodb.html`

The goal is **every MongoDB Compass feature, but more direct and more practical**. The engine structure follows `docs/ENGINES.md` (engine id `mongodb`, paradigm `document`).

## 2. Connecting

- Engine definition fields (in form order): connection string (`mongodb://`, `mongodb+srv://`; pasting one fills the other fields), host and port (27017), **authentication method** (None / Username and password / X.509 / AWS IAM / LDAP / Kerberos / OIDC; default None; a dropdown because there are many options), database (optional: the database to open first), TLS (off/on + CA and client certificate), `directConnection`, advanced: replica set name and read preference.
- Fields shown per authentication method (same layout as Compass). The same field can change its name and hint by method (the field's `variants`):
  - None: no authentication fields at all. You connect with only a host or a connection string. The server ignores any saved username and password (including the keychain) and any user in the connection string, and connects without authentication.
  - Username and password: username (required to connect), password (save in keychain / ask every time), authentication DB (`authSource`, default `admin`), SCRAM mechanism (default: server picks / SCRAM-SHA-256 / SCRAM-SHA-1). `PLAIN` in older profiles still works through this option. If the connection string names another mechanism (AWS, GSSAPI, OIDC, X.509), that mechanism is dropped and SCRAM is sent.
  - X.509: client certificate and key file fields appear, and TLS turns on. The server sends no password and always turns TLS on. If there is no certificate file (from the form or `tlsCertificateKeyFile` in the connection string), it stops with "X.509 authentication requires a client certificate and key file".
  - AWS IAM (`MONGODB-AWS`): access key ID (the username field), secret access key (the password field), session token (a second secret, optional). If the key ID is empty, nothing is sent and the driver looks for credentials in environment variables, profiles, ECS/EC2 roles, and web identity. If there is a key ID but no secret key: "Enter the AWS secret access key".
    - How the keys reach the driver: the key ID, secret key, and session token (form fields; if empty, `key:secret@` and `authMechanismProperties=AWS_SESSION_TOKEN:…` from the connection string) are given as an AWS credential provider (`Credential::aws_credential_provider`, fixed `Credentials` from `aws-credential-types`) set only in that connection's client options. They are not passed as username and password or as the `AWS_SESSION_TOKEN` property: mongodb crate 3.x warns "URI credentials for MONGODB-AWS are deprecated" and "`AWS_SESSION_TOKEN` … deprecated" when given that way, and 4.0 removes it (DRIVERS-3131, RUST-2248). The driver uses the provider before any other source (RUST-2249), so each connection signs with its own keys. Process environment variables are not touched, so other connections open at the same time (different keys, environment credentials) are not affected. Keys and the token are removed from the connection string before parsing (other `authMechanismProperties` stay), so the driver's connection-string check does not warn either. If the key ID is empty, no provider is set and the driver searches the AWS SDK default chain as before.
  - LDAP (`PLAIN`, `$external`): LDAP username and password (both required to connect). The authentication DB field is hidden and is always `$external`.
  - Kerberos (`GSSAPI`, `$external`): user principal (`user@REALM`), service name (default `mongodb`), service realm (optional), service host (optional), host name canonicalization (none / forward / forward and reverse). There is no password; the ticket from `kinit` is used. The ticket and realm settings follow the Kerberos setup of the TablePeek server process: the default cache and `krb5.conf`, or `KRB5CCNAME` and `KRB5_CONFIG` given when starting the server (macOS GSS.framework follows them too). The service principal is `<service name>/<host>@<realm>`. The host is the service host if set; otherwise the connect address (or, with canonicalization, the name resolved through DNS). If the server's principal is an FQDN (`mongodb/db.example.com`) but you connect via an IP, a tunnel end (`127.0.0.1`), or a load balancer name, put that FQDN in the service host, or add the name to the hosts file and connect with that name (no canonicalization). Otherwise the KDC does not know `mongodb/127.0.0.1` and it fails with "LOOKING_UP_SERVER". It is always included in macOS builds (GSS.framework). On other OSes it is included only with `cargo build --features kerberos` (needs Kerberos headers and libclang; libgssapi_krb5 at run time). Choosing it in a build without it says so.
  - OIDC (`MONGODB-OIDC`, `$external`): OIDC flow (browser login / Azure managed identity / GCP service account / Kubernetes service account), username (optional: login hint; for Azure, the managed identity's client ID), token resource (the audience, required for Azure and GCP). Browser login: §8.2.
- Pasting or typing a connection string updates the authentication method: if `authMechanism` is `MONGODB-X509`, `MONGODB-AWS`, `PLAIN`, `GSSAPI`, or `MONGODB-OIDC`, it becomes X.509, AWS, LDAP, Kerberos, or OIDC. Otherwise it is Username and password if there is a user (`user@`), and None if not. `SERVICE_NAME`, `SERVICE_REALM`, `SERVICE_HOST`, `CANONICALIZE_HOST_NAME`, `ENVIRONMENT`, `TOKEN_RESOURCE`, and `AWS_SESSION_TOKEN` in `authMechanismProperties` also fill their fields.
- A password is asked for only with methods that have a secret (username and password, LDAP, AWS with a key ID). When opening a saved connection with another method, the keychain is not read and no password is asked. None, X.509, Kerberos, OIDC, and environment AWS profiles are saved as not keeping a password in the keychain, regardless of the hidden storage choice (`persist_password: false`; with a tunnel, only the tunnel password is kept), and are listed with `has_password: false`.
- Older profiles without an authentication method (`auth`) get one filled in on read and on save: the method above if the authentication mechanism (field or connection string) is one of those five; Username and password if there is a username or password (including a user in the connection string); otherwise None. Connecting through the API without `auth` uses the same rule.
- SSH and HTTP tunnels: with a single host, one local end to that server is opened and the connection uses `directConnection=true`. `mongodb+srv://` and multi-host connections connect to each member behind the tunnel, as in §8.2.
- Passwords in connection strings (`user:password@`) are not saved. On save, the server removes the password from the string (the user stays). If the password field is empty, the password moves there and is kept in the keychain or asked each time, like any other password. Connection lists and export files also carry the string without the password, and the console, run history, and error messages mask URL passwords as `****`. When connecting directly without saving, the password in the string is used as is. (Same rule for every engine with a `uri` field.)
- Driver: the official `mongodb` crate (tokio). Server selection timeout 5 seconds; `maxTimeMS` on every query (the query timeout from settings).
- Capabilities: `language: "mongo"`, `objects: ["collection","view"]`, `schema: "sampled"`, `edit_by_key: true`, `foreign_keys: false`, `ddl: false`, `databases: "switch"`, `transactions`: `"replica_set"` if the connected topology is a replica set or sharded, `"none"` for a single server, `explain: "mongo"`, `indexes: { create, drop }`, `validation: true`, `aggregation: true`, `exact_count: false` (`estimatedDocumentCount` without a filter), `dump: "ejson"`.

## 3. Screens

### 3.1 Sidebar
Database → collections (document count), views (marked `Views`). Search, and right-click menus on databases and collections (phase 1: open, new query tab, refresh; phase 3: create, rename, drop).
- Click or Enter goes to the open tab for that collection (view, GridFS bucket), or opens a new tab if there is none. As in the SQL sidebar, middle-click, ⌘-click, ⌘↩, and `Open in new tab` in the menu open another tab even if one is already open (the same goes for indexes, aliases, and data streams in the search-engine sidebar). There are no preview tabs, so SQL's double-click (pin tab) and ⇧/⌘-click multi-select do not exist.

### 3.2 Collection tab
- Top: sub-tabs `Documents | Indexes | Explain` (phase 2 adds `Aggregate | Schema | Validation`, phase 4 adds `Changes`) + stat chips (document count, size, average size, index count and size).
- Query bar: a one-line filter (autocomplete: field paths, `$` operators, frequent values), an `Options` expander (projection, sort, skip, limit), `⌘↩` find, reset, recent runs and favorites, `Plan` (goes to the explain tab).
- Results toolbar: `+ Document`, expand/collapse all, (in JSON) EJSON toggle and copy page, and at the right end the **icon-only** view switch ☰ / {} / ⊞ (the name is given by tooltip and accessible name). The view is remembered per collection tab, `⌃1–3`.
- Bottom: range (`1–20 / 2,000 documents`), refresh, page size (10, 20, 50, 100; default 20), page navigation.

### 3.3 ☰ List
One card per document. Field name · value cell · type at the right end. Nested objects and arrays fold and unfold inside the card; folded, they show a preview such as `{4} { city: "東京", … }`.
- Clicking **anywhere** in a value cell edits it (type kept; invalid values show a message below the cell). Click the type label to change the type. Double-click a key to rename it. `+` adds a field or element, `✕` deletes.
- Changed fields are yellow, added fields green. Below the card: `n changes · Cancel · Save`.
- Card actions: edit JSON (`replaceOne`), duplicate, copy (EJSON), delete (with confirmation).
- Clicking a card header selects that card (blue border). When the list has focus, ↑/↓ select the previous or next card. The selected document appears in the right panel (§3.5).
- Mouse (same as the SQL grid): right-click (or ⌥-click) a field row for a menu — copy value, copy value as (mongosh, Extended JSON, JSON), copy field path, copy document, Quick Look, expand/collapse, edit (edit this value, rename, change type, set value EMPTY/null/new Date(), add, remove; these pile up in the card draft), query (filter by this value, exclude this value, only documents with/without the field → puts `{path: value}` in the filter and runs it right away; sort ascending/descending, clear sort; hide this field → projection `{path: 0}`). The path is the query path with array positions removed (`items.0.sku` → `items.sku`). Middle-click opens Quick Look for that value. Right-clicking a card header opens the document menu (copy document, copy _id, Quick Look, filter by this document, edit as JSON, duplicate, delete); middle-click opens Quick Look for the document; ⌘↩ with list focus opens Quick Look for the selected card.
- Clicking anywhere in a card or moving focus into it (including field editing) selects that card.

### 3.4 {} JSON
One block per document. mongosh notation (EJSON toggle), syntax colors, folding at every `{` and `[`. Hovering a block shows edit, duplicate, copy, and delete. Edit opens an in-place code editor (autocomplete, error position marks); `⌘↩` saves, Esc cancels. Clicking anywhere in a block or moving focus into it (including the editor) selects that block, and ↑/↓ select the previous or next block (press twice to edit). The selected document appears in the right panel. Right-clicking a line opens the menu for the value that starts on that line (the copy, Quick Look, fold, and query items of the card field menu, then document items); the block margin and first line open the document menu; middle-click opens Quick Look for that value (document); ⌘↩ with list focus opens Quick Look for the selected block. While editing, the browser's default menu is used.

### 3.5 ⊞ Table, and the right panel
- Uses the existing canvas grid. Columns are the top-level fields of the documents on the page (ordered by how often they appear). **No types in the header**; only object and array columns get `›`.
- Clicking an object or array cell or a `›` header opens just that field as its own table, with the path on top (`orders › items`). Documents inside arrays get one row per element (parent `_id`, `#` index). Several levels are possible.
- A missing field `—` (dimmed) is distinct from `NULL`.
- Cell edits keep the type; at lower levels they use a dotted-path `$set` (`items.0.quantity`).
- Mouse and keys (same as the SQL grid): right-click or ⌥-click a cell for a menu — copy (selection), copy value and as format, copy field path (with positions), copy document (documents of the selected rows), Quick Look, show row detail, open as sub-table, edit this cell, change type, set value (EMPTY, null, new Date()), remove field (`$unset`), filter by this value, exclude this value, only documents with/without the field, sort (query sort at the top level, in-table sort at lower levels), edit as JSON, duplicate document, delete document. Right-click a header — sort and clear sort, open as sub-table, copy field path, copy all column values, only documents with/without the field, hide this field. Middle-click or ⌘↩ on a cell opens Quick Look (the same popover as SQL); Space opens the right panel. The search-engine workbench uses the same view: filters are ANDed onto the query string as `field:"value"`, `NOT …`, `_exists_:field`; hiding uses the fields box (`-field`); sorting uses the sort box (`field:asc|desc`).
- Menus and Quick Look are tied to the document and field path at the time they opened. If the page reloads (save, F5, another page) or the sub-level or in-table sort changes, they close, and an item picked in between is not run; instead it says "The documents were reloaded, so this cell moved or is gone". Card and JSON block menus also close when their document reloads.
- Change type (table menu, the type label and field menu in cards and the right panel, and the same in the search-engine workbench): conversions that keep the whole value (between number types that hold the same number, strings that parse as is, to string, wrap in array, null and empty) happen right away. Conversions that lose the value (document or array → scalar, a string that does not parse as the target type, decimal → integer, a number beyond the precision, date → number, value → null, and so on) show the current and new values in an app confirmation dialog and change only after you press `Change type` (`keepsValue` in `valueEdit.ts`). Converting a decimal to Int32 or Int64 drops the fraction toward zero, like mongosh's `NumberInt` and `NumberLong` (1.5 → 1, -2.7 → -2). A number outside the target range becomes 0 and is also confirmed first.
- **Right panel**: the same app-level column as the row detail panel in SQL tabs. It stands at full window height beside the workbench (the whole editor, results, and console below the tab bar), and uses the same divider, remembered width (`tablepeek.detail-width`; double-click for the default width), drag-to-close (dragging below half the minimum width closes it), ⌘I, and the panel button on the tab bar. Open/closed is remembered per connection, as in SQL. The panel button on the table view's path row toggles the same state. The app owns the column (`DetailSlotContext`), and the view in front draws its selection into it (`DocDetailPanel`). A field search sits on top.
- The panel content follows what is visible.
  - ⊞ Table: the document of the selected row (at lower levels, the selected element and the path `orders › items › [0]`), shown with the same field rows as cards and edited and saved the same way (conflict check in §4). With several rows, common values and `Multiple values`.
  - ☰ List and {} JSON: the selected document with the same field rows, edited with the same conflict-checked save (view only for views and read-only connections). If a card and the panel edit the same document separately, each save sends its own original values as conditions.
  - With nothing selected, collection info: document count, size, average size, storage size, index count, and index size from `collStats`, plus each index's keys, options (unique, sparse, TTL, partial), and size (names and sizes from `indexSizes` if there is no permission to read `listIndexes`). It is read only while the panel is open, and re-read after saves and index changes.
  - Other sub-tabs: Aggregate shows result cards or blocks (read-only; the table view works like the table) or explain stages. Schema shows a summary of the field picked by clicking its name (presence ratio, type distribution, element types, sub-fields, summaries for numbers, dates, strings, ObjectIds, booleans, array lengths). Indexes shows the selected index's keys, options, size, and usage count. Explain shows the raw fields of the stage picked in the stage tree (input stages left out). Changes shows the raw selected event. Validation always shows collection info. With nothing selected, collection info. In lists, select by clicking or with ↑/↓.
  - Other tabs: the mongosh tab shows result cards or blocks (read-only) or table rows; otherwise info on the collection the results came from. A GridFS tab shows the selected file's `.files` document and a download; otherwise info on `<bucket>.files`. A database Changes tab shows the selected event. Performance and server info tabs show "This tab has no details to show".

### 3.6 Indexes tab
List (keys ↑/↓, UNIQUE, SPARSE, TTL, PARTIAL, compound; size from `collStats.indexSizes`, usage count from `$indexStats` — blank without permission), create (fields, direction, options, preview of the command to send), drop (with confirmation).

### 3.7 Explain tab
Runs `explain("executionStats")` with the current query bar contents. Stage tree (COLLSCAN, IXSCAN → FETCH → SORT …), documents returned and examined, keys examined, index used, bounds, time, warnings (full scan, in-memory sort, returned vs. examined ratio), raw view. Index suggestions (equality → sort → range order) with a create button.

### 3.8 mongosh tab
If every statement has one of these forms, the page parses it and sends a structured request (safe-mode confirmation possible per statement): `use`, `show dbs|collections`, `db.<c>.find(filter, projection).sort().skip().limit()`, `findOne`, `countDocuments`, `estimatedDocumentCount`, `distinct`, `aggregate([...])`, `insertOne/Many`, `updateOne/Many`, `replaceOne`, `deleteOne/Many`, `createIndex`, `dropIndex`, `getIndexes`, `drop`, `stats`, `.explain()`. Value notation: relaxed EJSON (unquoted keys, single quotes, trailing commas, `ObjectId()`, `ISODate()`, `new Date()`, `NumberDecimal()`, `NumberInt()`, `NumberLong()`, `/re/flags`). If even one statement does not parse (variables, functions, loops, and so on), the run range (selection, statement at the cursor, or everything for run all) runs as a JavaScript script in a Web Worker (§8.2). Results use the same three views. The parser lives in the web app (`web/src/engines/mongodb/shell/`); only structured requests go to the server. Autocomplete, highlighting, and re-running from history use this parser too.

### 3.9 Safe mode and console
- Writes with an empty condition (`updateOne`/`updateMany`/`replaceOne`/`deleteOne`/`deleteMany`), `drop`, and `dropIndex` get the safe-mode confirmation dialog. Once confirmed (or right away with safe mode off), the request is sent with `confirmed: true` — the server rejects writes with an empty condition that lack `confirmed`. Reads (`find`, `aggregate`, `count*`, `distinct`, `explain`) need no confirmation.
- Every action taken in the UI is logged to the console (⌘J) in mongosh notation.

## 4. Editing and conflict detection

If a document changed elsewhere after you opened it, it is not overwritten.

- The UI holds the **original values** from when the document was loaded. On save, each changed path adds its original value as a condition.
  ```js
  // changing status to "paid" and items.0.quantity to 5
  db.orders.updateOne(
    { _id: ObjectId("…"), status: "pending", "items.0": { sku: "P-0042", quantity: 2, price: NumberDecimal("19.90") } },
    { $set: { status: "paid", "items.0.quantity": 5 } })
  ```
  - When editing an array element by index, the whole element (`"items.0": { … }`) goes into the condition, which also catches a reordered array.
  - Adding a new field adds `{ field: { $exists: false } }`; removing one adds its original value.
  - `replaceOne` (JSON edit) does not use the whole document as the condition; it adds the original value of each top-level field of the loaded document.
- If `matchedCount == 0`, the document is re-read by `_id`. If it is gone: "Deleted elsewhere". If it exists: "Changed elsewhere", with **current value / your change** side by side, and a choice between `Reload the current value` and `Overwrite with your change` (overwrite uses only `_id` as the condition).
- Validation rule violations (`code 121`) show the rule message below that card or block.
- The server API takes these conditions and sends them as is (`GuardedUpdate { filter_guard, update }`). The rules that build the conditions live in the web app. UI edits always include `_id` in the condition.

## 5. Data transfer

- Documents travel as **canonical EJSON** (not Arrow). The web app handles BSON types as wrapped values (ObjectId, Decimal128, Int32/64, Double, Date, Binary, Regex, Timestamp, MinKey/MaxKey) and never turns Decimal128 into a float.
- The table view builds its table in the web app from the received documents.
- Large data:
  - Pages use `skip`+`limit` (default 20). If the sort is only `_id`, the next page is read from the last `_id`.
  - Document count is `estimatedDocumentCount` without a filter, `countDocuments` with one (3-second limit; past that it shows "many", and next pages still work).
  - A document over 1 MB or an array over 1,000 elements is truncated in the card and JSON views, with "Show all" to expand.
  - Schema samples use `$sample` with at most 1,000 documents (phase 2).

## 6. Server API (phase 1)

All take the `conn` query parameter and the same token authentication as before. Values in bodies and responses are canonical EJSON.

| Method and path | Body | Response |
|---|---|---|
| `GET /api/doc/databases` | — | `[{ name, sizeOnDisk, empty }]` |
| `GET /api/doc/collections?db=` | — | `[{ name, type: "collection"\|"view"\|"timeseries", options, count }]` |
| `GET /api/doc/stats?db=&coll=` | — | `{ count, size, avgObjSize, storageSize, nindexes, totalIndexSize, indexSizes }` |
| `POST /api/doc/find` | `{ db, coll, filter, projection?, sort?, skip?, limit, maxTimeMS? }` | `{ docs: [...], elapsedMs }` |
| `POST /api/doc/count` | `{ db, coll, filter }` | `{ count, exact }` |
| `POST /api/doc/aggregate` | `{ db, coll, pipeline, maxTimeMS? }` | `{ docs, elapsedMs }` |
| `POST /api/doc/distinct` | `{ db, coll, key, filter }` | `{ values }` |
| `POST /api/doc/insert` | `{ db, coll, docs: [...] }` | `{ insertedIds }` |
| `POST /api/doc/update` | `{ db, coll, filter, update, many: bool, upsert?: false, confirmed? }` | `{ matched, modified }` (single edits include the conflict condition in `filter`, `many:false`) |
| `POST /api/doc/replace` | `{ db, coll, filter, replacement, confirmed? }` | `{ matched, modified }` |
| `POST /api/doc/delete` | `{ db, coll, filter, many: bool, confirmed? }` | `{ deleted }` |
| `GET /api/doc/indexes?db=&coll=` | — | `[{ name, key, unique?, sparse?, expireAfterSeconds?, partialFilterExpression?, size?, ops? }]` |
| `POST /api/doc/indexes` | `{ db, coll, keys, options }` | `{ name }` |
| `DELETE /api/doc/indexes` | `{ db, coll, name }` | `{ ok }` |
| `POST /api/doc/explain` | `{ db, coll, find? \| aggregate?, verbosity: "executionStats" }` | Raw explain result |
| `POST /api/doc/command` | `{ db, command }` (only allowlisted commands such as `stats` and `drop` from the mongosh tab) | Raw result |

- Cancel: running reads (`find`, `count`, `aggregate`, `distinct`, `explain`) carry a `comment` tag (`tablepeek:<id>`) per request. When the existing WebSocket `cancel` arrives, `$currentOp` finds the operation with that tag and `killOp` ends it. Writes are not cancelled.
- Error codes: MongoDB error codes become `mongo_<code>` (for example `mongo_11000` duplicate key, `mongo_121` validation failure), with the original message. Errors without a code (network and so on) are `mongodb_error`. Violations of the rules below are `bad_request`; non-document connections get `unsupported_capability`.
- Write commands (`insert`, `update`, `replace`, `delete`, indexes, `drop`) are logged to the console and run history in mongosh notation (`db.getSiblingDB("shop").orders.updateOne({ … }, { … })`). The web app decides on safe mode. The server rejects only these: `update`, `replace`, or `delete` with an empty `filter` (`{}`, `null`, or omitted, regardless of `many`) and no `confirmed: true`; a `command` outside the allowlist (`collStats`, `dbStats`, `drop`, `listCollections`, `listIndexes`, `ping`, `buildInfo`, `serverStatus`), or `drop` without `confirmed: true`. A non-empty `filter` is sent as is even without `_id` (`db.c.updateOne({ status: "x" }, …)`). Document edits in the UI add `_id` and the conflict condition themselves.
- `count`: with an empty `filter`, `estimatedDocumentCount` (`exact: false`); otherwise `countDocuments` (3-second limit, `exact: true`). Past 3 seconds: `{ count: null, exact: false }`.
- `find`'s `limit` defaults to 20 when omitted. `aggregate` returns at most 10,000 documents at once. `explain`'s `find` is `{ filter, projection?, sort?, skip?, limit? }`, its `aggregate` is `{ pipeline }`. `size` and `ops` in the `indexes` list are `null` without permission.
- After connecting, `meta.capabilities.transactions` comes from the `hello` result: `"replica_set"` for replica sets and sharded clusters, `"none"` for a single server. `meta.tables` is the list of `db.collection`.

## 6.1 Server API (added in phases 2 and 3)

| Method and path | Body | Response |
|---|---|---|
| `POST /api/doc/aggregate` (changed) | `{ db, coll, pipeline, maxTimeMS?, confirmed? }` | Unchanged. A pipeline with `$out` or `$merge` counts as a write and gets `bad_request` without `confirmed: true` |
| `POST /api/doc/insert` (changed) | `{ db, coll, docs, ordered?: true }` | `{ insertedIds, errors: [{ index, code, message }] }`. With `ordered:false`, failed documents are skipped and the rest continue (for import) |
| `POST /api/doc/export` | `{ db, coll, filter?, projection?, sort?, limit?, pipeline? }` (with `pipeline`, the aggregation result) | NDJSON stream: one canonical EJSON document per line, last line `{"$end": { count }}`. Cancel by dropping the connection |
| `GET /api/doc/perf` | — | `{ time, uptime, process, opcounters, opcountersRepl?, connections, network, mem, wiredTiger?: { cacheBytes, cacheMax, dirtyBytes }, globalLock?: { activeReaders, activeWriters, queueReaders, queueWriters } }` (part of `serverStatus`; `process` is `mongod` or `mongos`; the web app polls every 2 seconds and computes per-second rates from the differences) |
| `POST /api/doc/command` (allowlist additions) | | `create` (collection, view, capped, timeseries, collation, validator), `renameCollection` (on admin, `confirmed`), `dropDatabase` (`confirmed`), `collMod` (validation rules, validationLevel, validationAction, TTL, hidden indexes; `confirmed`), `currentOp`, `killOp` (`confirmed`), `top`, `profile` (read with `-1`; changing the level needs `confirmed`), `hostInfo`, `replSetGetStatus`, `listDatabases` |

Schema analysis and validation rule testing use `aggregate` with no new routes: schema is `[{ $match: filter }, { $sample: { size } }]` (at most 1,000), documents that violate the rule are `[{ $match: { $nor: [validator] } }, { $limit: 20 }]`. Slow operations are read from the `system.profile` collection with `find`.

Details settled in implementation:

- `insert`: the response always has `errors` (`[]` if none). When `ordered` is sent, failed documents come back in `errors` (`code` is `mongo_<code>`, for example `mongo_11000`) and the response is 200. With `false` the rest keep going in; with `true` it stops at the failed document (only documents before it go in). `insertedIds` lists only the ids actually inserted, in send order. Without `ordered`, as in phase 1, the first failure makes the whole request a `mongo_<code>` error.
- `export`: errors before the first byte (`bad_request` for pipelines with `$out` or `$merge`, `mongo_<code>` while opening the cursor) are normal JSON error responses. A failure mid-stream makes the last line `{"$error": { code, message }}`, with no `$end`. Without `limit` or with 0, everything is exported. With `pipeline`, `filter`, `projection`, and `sort` are ignored and `limit` is appended as `$limit`.
- `perf`'s `network` is `{ bytesIn, bytesOut, numRequests }`; `opcounters`, `connections`, and `mem` are copied from `serverStatus`.
- `command`: `renameCollection` must be sent with `db: "admin"` (otherwise `bad_request`). `collMod` needs `confirmed` regardless of options (including a view's `viewOn` and `pipeline`); `create` does not. Changing commands (`create`, `collMod`, `renameCollection`, `dropDatabase`, `drop`, `killOp`, changing the `profile` level) and `$out`/`$merge` aggregations are also recorded in run history.
- `perf`, `export`, and `currentOp`, `killOp`, `top`, `serverStatus`, `hostInfo`, `replSetGetStatus` run outside the connection's execution gate. While a long query runs, the performance tab keeps updating and you can `killOp` that query. `$out`/`$merge` aggregations are writes and are not cancelled.
- Status reads the UI repeats are not logged to the console. `GET /api/doc/perf` is never logged. With `"poll": true` in a `command` or `find` body, the `currentOp`, `top`, `serverStatus`, `hostInfo`, `replSetGetStatus`, `listDatabases`, and `profile: -1` commands and `find` on `system.profile` are not logged to the console. Writes (`killOp`, changing the `profile` level, and so on) and other commands are logged regardless of `poll`. The driver `appName` is `TablePeek`, so TablePeek's operations can be identified by `appName` in `currentOp`.

### 8.2 Limits and how they were overcome

| Limit | Fix |
|---|---|
| No AWS IAM, LDAP, Kerberos, or OIDC authentication | Added authentication methods AWS (`MONGODB-AWS`, keys and session token, or environment and roles), LDAP (`PLAIN`), Kerberos (`GSSAPI`, service name, realm, host, host name canonicalization), and OIDC (machine: Azure, GCP, Kubernetes; human: browser login) (§2). All checked with real connections against Enterprise server test containers (§7): LDAP with OpenLDAP; Kerberos with an MIT KDC (`kinit` with a test-only `KRB5_CONFIG` and `KRB5CCNAME`, connecting via GSS.framework on a macOS host and via MIT `libgssapi_krb5` in a Linux container); OIDC with a local IdP (mock-oauth2-server, test CA certificate since HTTPS is required) for browser login (login page → callback → connect and find, cancel) and the Kubernetes flow (client-credentials token file); AWS with an STS stand-in that the server's `awsSTSUrl` points to (checks the signature with test keys and answers with an ARN), for keys, session token (assumed role), environment variable credentials, and a wrong secret key. Real AWS STS, ECS/EC2 roles, web identity, and the Azure and GCP metadata endpoints exist only inside the cloud, so they are checked only by unit tests (the credentials to send) |
| No Kerberos in Linux builds | GSSAPI links a system library: on macOS it is always on via GSS.framework; on Linux, turn it on with `cargo build --release -p tablepeek --features kerberos` (`tablepeek-engine/kerberos` → driver `gssapi-auth`). Building needs `libkrb5-dev` (MIT Kerberos headers) and `libclang-dev` (GSSAPI binding generation) on top of the default build's `build-essential`, `pkg-config`, and `libdbus-1-dev` (keyring); running needs `libgssapi-krb5-2`, and tickets need `kinit` (`krb5-user`). `make build-kerberos-linux` builds in a container based on the official Rust image (`rust:1-bookworm`) plus these packages and produces `target/linux/release/tablepeek` (for the Docker machine's architecture). `make test-live-linux ENGINE=mongodb-kerberos` uses the same container on the host network to reach the KDC and Enterprise server, and checks connecting with a ticket from MIT `kinit` (Docker Desktop needs host networking turned on) |
| X.509 not verified | A test server that requires TLS is in compose, using a test CA and server and client certificates (`testdb/x509/gen.sh`), and real connections are checked |
| No tunnel for SRV or multiple hosts | For `mongodb+srv://`, the server resolves SRV and TXT itself (SRV hosts must be in the same domain; TXT only `authSource`, `replicaSet`, `loadBalanced`; `srvServiceName` and `srvMaxHosts` honored; TLS on by default) and turns it into a connection string with the member list. The driver goes through a SOCKS5 relay inside the server for each connection (127.0.0.1, a random password per connection), and the relay opens an SSH (`direct-tcpip`) or HTTP (`CONNECT`) tunnel stream to the requested member name. Members keep their real names, so TLS certificate checks still match, and the driver handles primary discovery, rediscovery after `NotWritablePrimary` or network errors, and secondary selection for `readPreference=secondary` as usual. On a three-member test set, writing to the new primary over the same connection after `replSetStepDown` of the primary while connected over SSH is checked |
| Order of numeric-looking field names | The web app's document representation was changed to an order-preserving structure, and EJSON is parsed directly, so keys such as `"2024"` keep their original order |
| mongosh does not run JavaScript | Scripts run as real JavaScript inside a browser Web Worker. It provides `db`, collections, cursors, `print`/`printjson`, `use`, `show`, `EJSON`, and BSON constructors; server calls are synchronous requests from the Worker, so they are written without `await`, as in mongosh. It cannot touch the UI, storage, or token, and writes that need safe-mode confirmation report that the statement should be run on its own. Stop button and run time limit |

### 8.3 Server API additions

- `find`, `count`, `aggregate`, `explain`, and `export` bodies get `collation?` (document), `hint?` (index name string or key document), and `maxTimeMS?`. `update`, `replace`, `delete`, and `update/preview` also get `collation?` and `hint?` (same shapes, no `maxTimeMS`).
- `POST /api/doc/update/preview` `{ db, coll, filter, update, limit ≤ 20 }` → `{ matched, samples: [{ before, after }], previewed: bool }`. On servers with transactions, the first `limit` documents are actually updated and read inside a transaction, then rolled back (`abortTransaction`); on servers without them, only `previewed: false` and `matched`.
- `GET /api/doc/search-indexes?db&coll` → `[{ name, type, status, queryable, latestDefinition }]`; `POST` `{ db, coll, name, type?, definition }`; `PUT` `{ db, coll, name, definition }`; `DELETE` `{ db, coll, name, confirmed }`.
- `POST /api/doc/watch` `{ db, coll?, pipeline?, fullDocument?, fullDocumentBeforeChange?, resumeAfter? }` → NDJSON: one change event (canonical EJSON) per line, `{"$heartbeat": <ms>}` every 15 seconds; dropping the connection closes the stream. `resumeAfter` is the `_id` of the last event received (on reconnect, resumes after it).
- GridFS: `GET /api/doc/gridfs/buckets?db` → `[name]`; `POST /api/doc/gridfs/files` `{ db, bucket, filter?, sort?, skip?, limit }` → `{ files }`; `GET /api/doc/gridfs/download?db&bucket&id&token?` (id is a canonical EJSON string) → file bytes (name and length headers); `POST /api/doc/gridfs/upload?db&bucket&filename&metadata?` body = file → `{ id }`; `DELETE /api/doc/gridfs/files` `{ db, bucket, id, confirmed }`.
- Server cursors (`find()` and `aggregate()` cursors in the shell tab): `POST /api/doc/cursor/open` `{ db, coll, find?: { filter, projection?, sort?, skip?, limit?, collation?, hint?, maxTimeMS? } | aggregate?: { pipeline, collation?, hint?, maxTimeMS? }, batchSize?: 1–1000 (default 101), confirmed? }` → `{ id, batch, done }`; `POST /api/doc/cursor/next` `{ id, batchSize? }` → `{ batch, done }`; `POST /api/doc/cursor/close` `{ id }` → `{ ok: true, closed }`.
- Connection field `auth`: `none | password | x509 | aws | ldap | kerberos | oidc`, plus each method's fields (engine definition JSON): `oidc_flow` (`human | azure | gcp | k8s`), `aws_session_token` (secret), `kerberos_service_name`, `kerberos_service_realm`, `kerberos_service_host`, `kerberos_canonicalize` (`none | forward | forwardAndReverse`), `oidc_token_resource`.
- OIDC browser login: the server reads the discovery document using the IdP info (issuer, clientId, and scope given by the server), builds an authorization-code + PKCE (S256) request, and waits. `GET /api/oidc/logins` → `[{ id, url, issuer }]` (pending logins; if connecting takes more than 1 second, the web app asks every second and opens the login page from a notice at the top of the screen). `DELETE /api/oidc/logins?id=` → `{ ok }` (cancel; the connection fails with "Browser login was cancelled"). The IdP sends the browser back to `GET /api/oidc/callback?state&code` (this server's `http://127.0.0.1:<port>`). Only this route is accepted without a token, and it returns 400 unless `state` matches a pending login. The received code is exchanged for an access token at the token endpoint; if there is a refresh token, later refreshes happen without the browser. It fails after 5 minutes (driver limit). IdP requests trust the Mozilla roots and the system root certificates (corporate CAs); if `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, those certificates are used instead of the system ones.

Details settled in implementation (phase 4 server):

- Query options: `collation` is a document with `locale` (missing or invalid → `bad_request`); an empty `hint` string counts as no hint. `count`'s `maxTimeMS` replaces the 3-second limit when there is a condition (past it, still `{ count: null, exact: false }`); with an empty condition (`estimatedDocumentCount`), only `maxTimeMS` is used and `collation` and `hint` are ignored. `explain` puts `collation` and `hint` on the `find`/`aggregate` command being explained and `maxTimeMS` on the `explain` command. The console shows `find(…).collation({…}).hint(…).maxTimeMS(n)`, `aggregate([…], { collation, hint, maxTimeMS })`, and `countDocuments(…, { …, maxTimeMS })`.
- `collation` and `hint` on writes: `update`, `replace`, and `delete` send them through the driver's matching options, and the console shows them as the third argument (second for delete) (`updateMany({…}, {…}, { upsert?, collation, hint })`, `deleteMany({…}, { collation })`). `update/preview` uses both for counting and for finding the first few, and only `collation` on the per-document `updateOne`.
- `update/preview`: `limit` is 1–20 (default 5; out of range → `bad_request`). An empty `filter` is accepted without `confirmed` (nothing is left behind). `matched` is `countDocuments` (3-second limit), `null` past it. The first `limit` documents are updated one `_id` at a time with `{ $and: [filter, { _id }] }` (so the positional `$` operator works), re-read, and then always `abortTransaction`. If a document disappears during the preview, `after` is `null`. The console gets `countDocuments` and one `// preview: …abortTransaction()` line; nothing goes into run history. It runs like a read inside the connection's execution gate (can be cancelled).
- Search indexes: the list sends the server's documents as is (`id`, `name`, `type`, `status`, `queryable`, `latestDefinition`…; `type` is `"search"` if missing). `type` accepts only `search` and `vectorSearch`. Errors from servers without Atlas Search (`31082` SearchNotEnabled, `6047401` Atlas-only stage, `40324`, `59`, `115` on older servers) become `unsupported_capability` (with the original message). Create, update, and drop are logged to the console and run history as `createSearchIndex({ name, type?, definition })`, `updateSearchIndex(name, definition)`, and `dropSearchIndex(name)`.
- `watch`: right after opening it first sends one `{"$heartbeat": <epoch ms>}` line, then one every 15 seconds. A single server gets `unsupported_capability` before opening. Invalid `fullDocument` (`updateLookup`, `whenAvailable`, `required`; `default` is the same as omitting it), `fullDocumentBeforeChange` (`whenAvailable`, `required`, `off`), or `resumeAfter` → `bad_request`. A failure mid-stream makes the last line `{"$error": { code, message }}`; when the stream ends (after an `invalidate`, such as a collection drop), the connection is closed. Without `coll`, it watches the whole database. Like `export` it runs outside the execution gate; when the page drops the connection, the next line (at the latest, the heartbeat) cannot be sent and the server cursor closes.
- GridFS: upload writes the body into chunks (255 KiB) as it arrives, so the whole file is never held in memory; if the body is cut off midway, chunks already written are deleted. Download also reads and sends chunk by chunk. Both run outside the execution gate. Response headers are `Content-Type` (the file document's `contentType`, else `application/octet-stream`), `Content-Length`, and `Content-Disposition: attachment; filename*=UTF-8''…`. A missing file is 404 `not_found`. Only download accepts `token` as a query parameter (for `<a download>` links; the header also works). `metadata` is canonical EJSON text; `files` returns the `.files` documents as is (including `contentType`, `md5`, and so on). The console and run history get `mongofiles --db=… --prefix=<bucket> put|get_id|delete_id …` (`# metadata: {…}` after `put`). A bucket is a name for which both `<name>.files` and `<name>.chunks` exist.
- Server cursors: kept in a table per connection (slot), holding the driver cursor open as is. They close when read to the end (`done: true`), on `close`, when the connection closes, or after 10 minutes without reads (checked every 30 seconds), and the server-side cursor closes with them (`killCursors`). Up to 32 per connection; past that, the one unread the longest is closed. If the first batch finishes it, `id` is `null` (nothing to close). Omitting `batchSize` on `next` uses the size from open. A missing or closed `id` is 404 `not_found`; reading the same cursor concurrently is `cursor_busy`; a failure while reading sends that error and closes the cursor. The console logs it once on open as `find(…)….batchSize(n)` / `aggregate([…], { …, batchSize: n })`. `$out`/`$merge` aggregations need `confirmed: true` and run as writes (inside the execution gate, recorded in run history); other cursors read outside the gate like `export` (`find` with no `limit` or 0 reads everything; `aggregate` results have no 10,000-document limit).

Details settled in implementation (phase 4 UI):

- Bulk update and delete: `Bulk update` and `Bulk delete` on the documents tab toolbar (absent for views and read-only connections) open the same dialog, and you can switch between update and delete at its top. The filter starts from the current filter text in the query bar; editing it in the dialog leaves the query bar unchanged. The collation and hint from the query bar's `Options` are fixed when the dialog opens and go along with counting, preview, and execution (`update`, `delete`, `update/preview`); the command to send shows them as mongosh's third argument (second for delete) `{ collation, hint }` (no time limit is sent). The update is an operator document (`{ $set: { } }` template, all keys start with `$`, empty operators rejected) or a pipeline (one operator per stage). When typing pauses for 0.5 seconds, it re-reads the number of affected documents with `count`; for update, the before/after of the first 5, 10, or 20 with `update/preview` (per field: changed yellow, added green, removed red; nested documents expand inline; `Changed fields only`); for delete, the first few to be deleted with `find`. `⌘↩` re-runs right away. With `previewed: false`, it says the server is a single server without transactions so no preview is possible, and shows the current state of the documents that would change with `find`. Execution always adds `confirmed: true` to `updateMany`/`deleteMany`, and safe-mode confirmation follows the same rules as the mongosh tab (an empty filter is dangerous at levels 1 and 2; level 2 covers all bulk writes). The result (matched and modified, or deleted count) appears at the bottom of the dialog, and the document page and stats are re-read. With 0 affected documents, the run button is disabled.
- mongosh scripts (`shell/worker.ts`, `shell/script.ts`): a new Worker per run. `use x` and `show dbs|collections` lines are turned into `use("x")` and `show` calls before running (line numbers kept); the rest runs through indirect `eval`, and the value of the last statement is shown as the final value. Numbers are Int32 if they are 32-bit integers, like the Node driver, and Double otherwise; `bigint` is Int64; `Date` and `RegExp` are BSON dates and regexes. Documents read back are plain objects that keep field order (Int32 and Double as numbers, dates as `Date`, Int64, Decimal128, and others as BSON values). The BSON constructors accept everything the app's mongosh notation and code export use (`ObjectId`, `ISODate`, `NumberLong`/`Long`, `NumberInt`/`Int32`, `Double`, `NumberDecimal`/`Decimal128`, `UUID`, `BinData`, `Binary.createFromBase64`, `Timestamp`, `Code`, `BSONRegExp`, `MinKey`/`MaxKey`). `find` and `aggregate` cursors read server cursors (`/api/doc/cursor/open`, `next`, `close`) 1,000 at a time, and open cursors are closed when the script ends (cursors of a stopped Worker close on the server's idle timeout). If the final value is a cursor, the first 1,000 are shown. Output: `print` lines as text; `printjson`, a single object passed to `print`, and the final value pile up in messages as values, and values that are documents open in the ☰ {} ⊞ views via `Show results` or by picking `output n`. Output is capped at 1,000 items and 16 MB (the final value is always shown). The time limit is the `Query timeout` setting (default 60 seconds, 0 for none; it is also the default `maxTimeMS` for collection tab queries), and each read sends the remaining time as `maxTimeMS`. Stop and timeout terminate the Worker. With safe mode on, writes that would need a confirmation dialog (same as the run-alone rule, plus `$out`/`$merge` aggregations and `runCommand` calls that need confirmation) are not sent; the script stops with an error saying to run that statement on its own or turn off safe mode. With safe mode off, writes get `confirmed: true`. Before the script starts, network and storage globals (`fetch`, `XMLHttpRequest`, `WebSocket`, `importScripts`, `indexedDB`, `caches`, `navigator`, `postMessage` …) are removed, and the token stays inside the module, passed only to request functions captured beforehand.
- Search indexes: the `Search indexes` section below the index table on the indexes tab. Name, type (`search`, `vectorSearch`), status (READY green, FAILED red, anything else building yellow), queryable, and a one-line definition. While an index is building or being dropped, it re-reads every 5 seconds. The create and update dialog has name and type (both fixed when updating), a definition editor (mongosh notation or JSON) with three templates (dynamic mapping; field mapping — the first top-level field of the sample; vector search — takes `path`, `numDimensions`, and `similarity` from fields and builds `{ fields: [{ type: "vector", … }] }`), and the command to send. Drop sends `confirmed: true` after a confirmation dialog. On `unsupported_capability`, instead of an error it shows only "Search indexes are not available on this server" with a note on where they are available, and hides the create button.
- Changes: a sub-tab of the collection tab (not on views) and `Changes` in the sidebar database menu (whole database, one tab, with a collection column added). The session lives per tab while the page is alive (`changeStream.ts`), and the stream is open only while that view is visible. Moving to another tab or sub-tab closes it; coming back reopens it with the `_id` of the last received event as `resumeAfter`, so changes in between arrive too. If the connection drops or a `$error` arrives, it reconnects the same way at 1, 2, 5, 10, and 30 second intervals (`unsupported_capability`, `bad_request`, `invalid_token`, `not_found`, `mongo_286`, `mongo_280`, `mongo_13`, and `mongo_47` stop and show the error; `Try again` opens fresh without a token). When the server closes after `invalidate`: "The server closed the stream". The operation type filter (insert, update, replace, delete, other) is applied after receiving, not as a pipeline `$match`, because reopening with the token of a filtered-out event makes MongoDB 7 reject it with "resume token was not found". So changing the filter does not reopen the stream; changing `Document after` (`fullDocument: "updateLookup"`) or `Document before` (`fullDocumentBeforeChange: "whenAvailable"`; arrives only if the collection has `changeStreamPreAndPostImages` turned on) reopens it after the last event. The list is newest first, up to 1,000 (overflow count shown). A row shows the time (`wallTime`, else `clusterTime`), type, `_id`, and a summary (fields set and removed, field count, rename targets); expanding it shows a before/after table of changed fields (the before value is looked up by path in the pre-change document), the pre- and post-change documents, and the raw event with copy. Events are drawn in batches per animation frame. `Pause` keeps the token so `Start` resumes; `Clear` only clears the list.
- GridFS: the sidebar shows a name with both `<b>.files` and `<b>.chunks` as one bucket row with a `GridFS` badge (the count is the file count); clicking opens the bucket tab, and the arrow expands the two collections. The bucket tab is a file table (name, size, upload time, content type — top-level `contentType`, else `metadata.contentType` — and metadata; click headers to sort; pages of 50; the total is `count` on `.files`). The search box does a case-insensitive partial match on file name (`$regex`) for text, or takes a filter document if it starts with `{`. Downloads are links with `token` in the query, so the browser fetches them directly. Upload by picking files (several) or dragging them onto the list, with a progress bar and cancel per file; files go one at a time (XHR `upload.onprogress`), and the MIME type the browser knows goes into `metadata.contentType`. Delete happens after a confirmation dialog (preview of `mongofiles … delete_id`). `View` shows the whole file document as read-only fields.
- Query options: the second row of the query bar's `Options` (`QueryOptionsRow.tsx`). collation is a locale (common locales suggested; any supported locale works) and strength (default, 1–5) — picking a strength without a locale is a query bar error. hint is picking a collection index name (empty list for views) or, by choosing `Write a key document…`, a `{ … }` editor (an empty document is an error). maxTimeMS is an integer of 1 or more (milliseconds); empty means the query timeout from settings. All three are saved with the query text in tab state (`doc.query`, `doc.applied`) and in recent runs and favorites (previously saved queries read as empty), and reset clears them too. They are attached to the document page's `find`, the total `count` (maxTimeMS, if set, replaces the 3-second limit), exact count, explain's `explain`, and export (`export`; the `count` for the estimate uses only collation and hint; the CSV field sample `find`), and appear in the command to send and the explain row as `.collation({…}).hint(…).maxTimeMS(n)`.
- To code (`codegen.ts`, `CodeExportModal.tsx`): `To code` on the documents tab toolbar turns the query bar's current query (the last run query if the text is invalid) with its options into code; `To code` on the aggregate tab (where `mongosh code` used to be) turns the pipeline of enabled stages into code. Languages: mongosh, Python (PyMongo), Node.js (ESM), Java (sync, `Document`), C# (.NET, top-level statements), Go (driver v2, maxTimeMS as a context deadline), Rust (`mongodb` 3, `doc!`), PHP (`mongodb/mongodb`), Ruby. Values are written in each language's type: ObjectId, Int64 (`Int64(…)`, `Long`, `5L`, `int64(…)`, `_i64`…), integral Double (`Double(3)`, `3.0`…), Decimal128, dates (ms for years a calendar cannot represent), regexes (the BSON regex type; JS and mongosh literals only when the pattern has no `/`), Binary and UUID (subtype 4), Timestamp, Code, MinKey/MaxKey. With `Include connection code`, the output is a program that connects, runs, and prints, using a connection string built from the connection settings (`/api/connection-info`: the saved profile for saved connections, the opened settings for unsaved ones; the server strips secrets) with `<password>` in place of the password and `authMechanism`, `authSource`, and properties per authentication method. Without it, only the query part, assuming a connected `client`. The language and connection-code choice are kept in localStorage. mongosh also offers `Open in a mongosh tab`. Cursor methods are attached to the last line of the call (the mongosh prompt reads lines starting with `.` as REPL commands). Each language's code was actually compiled and run against the test DB to confirm every type arrives as the same BSON type and value (with `$type` and `$eq`).
